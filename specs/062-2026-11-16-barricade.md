## Context & Background

Barricade is the security engine of the platform: its detections and their automated responses (user decision, 2026-11-16). This screen is only its configuration, with its own icon (`src/assets/barricade.svg`: an agent behind a brick wall, guarded by a shield). It is a tab of the account area, after Events export (user decision, 2026-11-16). Each environment of a workspace has its own setting (Backend 101), so the page picks a workspace and an environment.

---

## Solution

Draft, from the prototype:

1. Account tabs: Workspaces, Events export, **Barricade**, Account info. Barricade uses the Barricade icon.
2. **Heading**: the title, then the scope: a workspace select (the workspaces where the person is Admin), an environment select (Production, Sandbox) and **Change history**.
3. **A rail of security modules** on the left, as the Access workbench rail (docs/design-system/layouts.md). Behavior drift is the first module; the page grows by adding modules to the rail, each with its own editor (user decision, 2026-11-16: the page will hold many security settings).
4. **The module editor**: its name and the last change (who and when, or the market defaults since the environment was created), then:
   - **Detection**: the five heuristics of Backend 099, with the values stored for the environment.
   - **Automated response**: one row per anomaly (Usage spike, First use of a tool, Unusual call sequence) with an action: Alert (a signal in the Inbox), Suspend the tool for this agent, or Disable the agent; a warning when an action blocks calls. The page never names a delivery app (user decision, 2026-11-16). The choice is stored in the configuration and executed by the behavior drift module; both ship in the same deploy (user decision, 2026-11-16).
   - Cancel and Save on the right, as an editor of one item.
5. **Change history**: a wide side panel (docs/design-system/layouts.md) with every change of the environment's setting, newest first: when, who, and what changed.
6. Wording in security terms (user decision, 2026-11-16): anomaly, baseline, detection, automated response.

## Backend dependencies

- Read and save the Barricade setting of a workspace environment, and read its change history: [Backend 101](../../backend/specs/101-2026-11-16-barricade-settings.md), Implementation Decision 6. A refused setting returns `invalid_barricade_setting` with its `field`; the Admin names that field.

## Acceptance Criteria

- [ ] 1. The user approves the layout of the prototype.
- [ ] 2. The account tabs show Barricade after Events export, with the Barricade icon; it opens `/account/barricade`.
- [ ] 3. The workspace select lists the workspaces where the person is Admin, and the environment select their environments, Production first. Each environment shows its own stored setting; the Admin holds no default values.
- [ ] 4. The module editor shows the last change: who (name and email) and when, or the market defaults and the date they were stored (the creation of the environment, or the Backend 101 migration for an older environment).
- [ ] 5. Detection shows the five heuristics of the environment. Save stores them; Cancel returns to the stored values; both are enabled only after a change. A value the backend refuses shows the name of its field and changes nothing.
- [ ] 6. Automated response shows one action per anomaly: Alert, Suspend the tool for this agent, or Disable the agent. A blocking action shows the warning that calls will be blocked automatically. The page names no delivery app.
- [ ] 7. Change history opens a wide side panel with every change of the environment, newest first: when, who (Platform for the creation) and what changed, paged.
- [ ] 8. The prototype route is removed and the prototype is Archived in `specs/prototypes/README.md`.
- [ ] 9. `npm run check` and `npm run build` pass.
- [ ] 10. Functional test: [062-2026-11-16-barricade.md](functional-tests/062-2026-11-16-barricade.md)
