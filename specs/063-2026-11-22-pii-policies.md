## Context & Background

The response of a tool reaches the agent exactly as the MCP server sent it: the PEP checks only the JSON-RPC envelope and its size (`backend/internal/pep/proxy_response.go`). The roadmap of the session rules (Backend 097, Context) promises that secrets and personal data are removed before they reach the agent, in a separate specification. Backend 105 defines that cleaning; this specification is its configuration in the Admin.

Barricade (Admin 062) is the configuration of the security engine, per environment of a workspace, with a rail of security modules. PII Policies is its second module, and this specification turns the rail into inner tabs.

---

## Problem Statement

### 1. No control over personal data and secrets in tool responses

A tool that reads a customer record, an email or a configuration file hands every CPF, card number or API key in it to the agent, and from the agent to the model provider and its context. An administrator has no place to say which kinds of data an agent may receive.

### 2. One rule does not fit every agent

An agent that answers customers needs their email and phone; a refunds agent does not. A single setting per environment would force the administrator to open a type to every agent because one needs it.

---

## Solution

From the approved prototype:

1. **A module of Barricade** (user decision, 2026-11-22): a second security module, **PII Policies**, after Behavior drift, with its own editor. Same scope as Barricade: one setting per environment of a workspace; Sandbox and Production are set apart.
2. **Modules as inner tabs** (user decision, 2026-11-22): the security modules are design-system inner tabs (`cp-admin-inner-tabs`) above the module editor, which takes the full width. They replace the rail of Admin 062, which does not follow the Admin design system; the real Barricade page changes with this specification.
3. **Masked types per environment** (user decision, 2026-11-22): the administrator chooses which entity types are masked. The types are shown in categories (Secrets, Documents, Financial, Contact, Person, Network), each type with its placeholder and a switch. Each category is a neutral design-system accordion (`cp-admin-accordion`) whose summary has its name, how many of its types are masked and, below, its one-line description (user decision, 2026-11-22); only the first category is open, on the page and in the agent side panel (user decision, 2026-11-22). The neutral accordion gains in the design system the chevron of the toned accordions and the `color-hover` of its summary (user, 2026-11-22: the accordion had no hover). The types, their keys, groups and placeholders come from the catalog of Backend 105 (Implementation Decisions 7 and 8, `GET /api/v1/pii/entity-types`): Secrets (Password, API key, Access token), Documents (National ID number, which includes tax numbers, Passport number, Driver's license number), Financial (Payment card, Bank account), Contact (Email, Phone number, Address), Person (Date of birth), Network (IP address). Person name left the catalog when Backend 105 removed its detection model (2026-11-23): no pattern finds a name. The note that Address is detected less reliably left with the model; Address is now found by street types, suffixes and postal codes (Backend 105, Implementation Decision 7).
4. **Mask, never block** (user decision, 2026-11-22): a value of a masked type is replaced by a typed placeholder (`{EMAIL}`, `{NATIONAL_ID}`) in the tool response before the agent reads it. Only the response; the arguments of a call are never changed.
5. **Secrets in scope** (user decision, 2026-11-22): password, API key and access token are types of the same module.
6. **Deploy defaults** (user decisions, 2026-11-22; Backend 105, Implementation Decision 12): secrets and document and financial identifiers masked; email, phone number, address, date of birth and IP address not masked.
7. **Per agent, never per tool** (user decision, 2026-11-22): an agent follows the masked types of its environment, or has its own policy. The Agents table lists each agent of the environment with its policy as a badge (Environment: follows the masked types of the environment; Own policy: its own list, which later environment changes do not reach; kept by user decision, 2026-11-22) and the difference from the environment, with Edit, and the list pager under it (user decision, 2026-11-22). Edit opens a side panel with no policy select (user decision, 2026-11-22): the badge of the agent's policy and one line that says it, the type list with the environment value and the agent switch, always editable, and **Reset to environment** when the agent differs from its environment. The policy follows from the switches: a change to any switch makes the agent use an own policy, and the saved own policy is the whole list as the switches show it, the unchanged ones included, never a merge with the environment (user confirmation, 2026-11-22; Backend 105, Architecture Gate); a later change of the environment does not reach it. A save with no difference from the environment removes the own policy, so the agent follows its environment again; Reset to environment sets every switch back to the environment in the draft, and Save applies it. An own policy that has the same types as its environment, after a later change of the environment, stays an own policy: the table shows Own policy and Same as the environment, and the panel shows Own policy, says that a later change of the environment does not reach the agent, and offers Reset to environment, whose Save removes the own policy (formal review, 2026-11-23).
   - **Where the defaults live** (Backend 105, Implementation Decision 9): the masked types of the environment are the `pii_policies` section of its Barricade setting, created with the deploy defaults. The agent keeps only its own policy, under `agents`; an agent without one follows its environment.
   - **A new agent** has no own policy, so it follows the masked types of its environment from its first call; nothing is written when it is created (Backend 105, Architecture Gate: an absent policy follows the environment).
8. **Report-only** (user decision, 2026-11-22): for an agent in Report-only nothing is masked; each call with a value of a masked type is recorded as would mask, with the types found. The module does not state it (user decision, 2026-11-22); the Report-only chip beside the agent name stays.
9. **Detection failure** (user decision, 2026-11-22): fail-open. If detection does not answer, the response reaches the agent unmasked and the Inbox gets a High signal. It is not a setting, and the module does not state it (user decision, 2026-11-22).
10. **No values** (user decision, 2026-11-22): the values found are never shown or stored, only their types and counts. The module does not state it.
11. **No model name**: the screen never names the detector or its model.
12. Cancel and Save on the right, as an editor of one item (Admin 062). Changes go to the Barricade change history, with who changed it, when, and the setting before and after (Backend 101, Implementation Decision 2: `barricade_setting_changes.changed_by`; Backend 105, Implementation Decision 9).
   - **Change history with PII changes** (prototype `HistoryPanel`, user request 2026-11-22): the same panel, table and pager as Admin 062 (When, Who, Change). Each change line starts with its module (`PII Policies ·` or `Behavior drift ·`). PII lines: a type of the environment (`Email: not masked → masked`), an agent that gets an own policy with the types where it differs (`refunds-assistant: own policy, Email, Phone number, Date of birth masked`), an agent back to the environment, an own policy removed with a deleted agent (its author is the person who deleted the agent, Backend 105). The migration to the PII policies writes no history entry (Backend 105, Implementation Notes 3; user decision, 2026-11-23): the first save of an environment shows its change from the setting before PII Policies. The implementation extends `describeChange` (`src/features/account/barricade-terms.ts`) with the `pii_policies` section of version 2 and adds the module prefix to the Behavior drift lines.
   - **Manage shortcut** (user decision, 2026-11-22): before the history button, while PII Policies is the chosen module, a **Manage** button of the same size and style scrolls to the Agents table at the end of the page.
   - **History button** (user decision, 2026-11-22): the Change history button of Barricade is named **History**; the panel it opens keeps the title Change history.
   - **Module heading** (user decision, 2026-11-22): the module name and only a badge of the chosen environment. No last change line; who changed it and when are in Change history.
13. **Unsaved changes ask first** (user decision, 2026-11-22): with unsaved changes, Cancel of the module and, in the agent side panel, Cancel, the close button, Escape and a click outside open the dialog **Save your changes?**, which names what changed. It is not a destructive confirmation: **Save** (primary) saves and closes, **Discard** (`cp-admin-button--danger-soft`) drops the changes and closes, and **Keep editing**, Escape or its close button return to the editor. Without changes they close at once.
   - **Leaving the screen** (user decision, 2026-11-22): with unsaved changes in the module, the same dialog opens before any way out of it: another account tab, the Behavior drift module tab, another workspace or environment, and in the implementation every other navigation of the Admin (the router blocker that the Inbox detail already uses, `src/app/AppRoutes.tsx`). Save saves and then goes on; Discard drops the changes and then goes on; Keep editing stays. A reload or a closed browser tab can only show the native prompt of the browser (`beforeunload`).
   - It is a new design-system dialog, built on the design-system Dialog; the implementation adds it to `src/components/ui/dialog` and documents it in the design system.

14. **PII filter switches** (user decisions, 2026-11-22; they replace the general workspace switch drawn before).
   - **Environment switch**: one per environment (`pii_policies.enabled`). Off in a new workspace and in every workspace that exists at the deploy, so nothing is masked until an Admin turns an environment on. The masked types and the agent policies are kept in every case; the switch never changes them.
   - **Workspace**: no switch and no state of its own (user decision, 2026-11-22; confirmed 2026-11-23: a workspace has N environments, today Production and Sandbox, and turning any of them on turns the workspace on implicitly). The Barricade Workspace select shows it green while one of its environments is on, red when all are off.
   - **Agent**: the Agents table of PII Policies has a **PII filter** column with one status switch for each agent, on by default (a new agent is on). An agent belongs to one environment (Backend 005: `environment_id` is part of its key, and an agent never moves between environments), so the table lists the agents of the chosen environment and each has the switch of that environment only (user decision, 2026-11-23, at implementation; the prototype drew one switch per environment on each agent, which the backend has no agent for). Off: the agent gets its responses unmasked, and its policy (environment or own) is kept. An agent is filtered only while its environment and its own switch are on; its switch is disabled, and shows red, while the environment is off. It applies at once, with no Save, and goes to the history.
   - **Under the agent name** (user decision, 2026-11-23, at implementation): its description, which the agent list already returns, instead of its MCP server, which would take one permissions read per agent.
   - **Workspaces list** (account area, Admin 051): only environment switches, as the Agents table of PII Policies (user decision, 2026-11-22). The **Environments** column, which today shows only badges, becomes **PII filter by environment**, with one switch per environment (Production, Sandbox). Each switch applies at once, with no Save, and goes to the history with its author.
   - **Status switch and status dots**: the switches are the design-system status switch (`cp-admin-switch--status`): green (`--cp-admin-color-success`) when on, red (`--cp-admin-color-danger`) when off, with no dot beside them. The Workspace and Environment selects of Barricade, which have no switch, show a dot with no border in the same colors before each option and the chosen value, with its text for readers (PII filter on or off); the implementation adds an optional status to the options of `SelectMenu` (design system).
   - Prototype page: `/account/prototype/pii-workspaces`.
   - **Consequence for the deploy defaults** (item 6): the masked types of item 6 apply from the moment an environment is turned on.

## Backend dependencies

All defined in [Backend 105](../../backend/specs/105-2026-11-22-pii-cleaning-of-tool-responses.md) (Not Implemented); every `Waiting backend · 105` chip of the prototype waits for it:

- The masked types of an environment and the own policies of its agents, in the Barricade setting version 2, with its routes and change history (Implementation Decision 9).
- The catalog of entity types with key, group and placeholder (Implementation Decisions 7 and 8).
- The deploy defaults (Implementation Decision 12).
- The PII filter switch of each environment (`pii_policies.enabled`, off by default and at the deploy) and of each agent in an environment (`pii_policies.agents.<agent_id>.enabled`, on by default); no workspace switch, the Admin derives it (Implementation Decision 18b).
- The would mask record of an agent in Report-only and the High signal of a detection failure (Solution 6 and 7).

---

## Out of Scope

- Masking of call arguments (user decision, 2026-11-22). Backend 105 detects and records their types without changing them (Implementation Decision 18a); showing that record is not part of this screen.
- A policy per tool (user decision, 2026-11-22).
- Blocking a response that holds a masked type.
- How masked calls show in Investigate and the Inbox: a later step of this layout.
